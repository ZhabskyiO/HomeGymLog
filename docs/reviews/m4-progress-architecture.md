## Blocking

**B1 — `ProgressSession` cannot compute `plannedFallbackLb` (§4.3 `ProgressSession`, §5.4, AC-18).** §5.4 says Best falls back to "the `targetWeightLb` of the key's element in the current program's lowest-index session that plans it", but §4.3 defines `ProgressSession.exerciseKeys: [String]` (keys only, no targets). The Engine function `plannedFallbackLb(key:sessions:)` has no weight to return. It is also a second session value type parallel to `SessionSummary` (`/Users/zhabskyi/AppleApps/HomeGymLog/HomeGymLog/Engine/HomeStatsTypes.swift:4-15`), which already carries `exercises: [PlannedExercise]`, `index`, `scheduledDate` and `status`, and is what `HomeStats.sessionState` (reused by §5.5) takes.
*Change:* `ProgressSession { programID: UUID; programCreatedAt: Date; isArchived: Bool; summary: SessionSummary }` (or the three program fields plus `exercises: [PlannedExercise]`); `exerciseKeys` becomes `summary.exercises.map(\.key)`. The builder reuses `HomeSnapshotBuilder.sessionSummaries` for the inner value. `ProgressStats.plannedFallbackLb` reads `exercises.first { $0.key == key }?.targetWeightLb` (whatever the element's field is named). Update §4.3 and AC-18's fixture description.
*React:* wrap the existing value type rather than declaring a second interface with half its fields; `HomeStats.sessionState` is the selector you want to call without adapting.

**B2 — `ProgressPoint` identity must never be the session index (§4.3 `ProgressPoint`, §4.4 chart recipe, §5.2, AC-7).** The researcher's recipe (`TopWeightPoint.id = index` where index is the session index, report "Code example") is what §4.4 tells the planner to copy. With D2, two programs contribute points and `PlannedSession.index` restarts at 0 in every program: in `progress-history` the archived s0 (Aug 3, dbBench 40) and the current s0 (Aug 31, 37.5) collide, so `ForEach(points)` gets duplicate ids and SwiftUI's rendering of duplicate identities is undefined (usually a missing or mis-drawn mark, sometimes a runtime warning). The x value is already the point's position (`.value("Session", i)`), which is the right identity too.
*Change:* in §4.3 give `ProgressPoint` (or the sorted `ProgressTop`, see NB3) an `id` = its position after ordering, or `(programID, sessionIndex)`; in §4.4 say "identity is the point's position, never `sessionIndex` (indexes repeat across programs)". AC-7 becomes the regression check (seven distinct dots), and AC-16's "two programs' points interleave" test should assert the positions 0…n−1 are unique.
*React:* a `key={session.index}` that repeats across two lists merged into one.

**B3 — The per-key task is keyed on the selected key, not the effective key, and holds no key with its result (§4.1 "Points of the selected key", §4.4 "Screen state", §6 "Stale selected key").** §4.1 runs the fetch "in `.task(id:)` keyed on (selected key, fingerprint)"; §6 says a stale selection "falls back to the first chip (no write)". With `-progressExercise nope` (or a key gone after a restart), `selectedKey = "nope"`, `effectiveKey = dbBench`, and the task fetches `"nope"` → no rows → the card shows the empty state under a chip that has three points. Separately, a synchronous fetch inside a cancelled task still assigns `points` unless the assignment is guarded, so a fast chip tap can draw the previous key's line under the new chip for a frame.
*Change:* key the task on `(effectiveKey, fingerprint)` and store `@State held: (key: String, points: [ProgressPoint])?`, drawn only when `held.key == effectiveKey` (the m3-exercise-tools pill-baseline shape, INSIGHTS 2026-09-14 "Pill baseline ownership"; `WorkoutView.swift:121`). Never clear `points` before a fetch (a tab return re-runs `.task`, NB6; clearing would flash the empty line). `.task(id:)` needs an `Equatable` id: a tuple is not one, so use a small `struct` or `"\(key)|\(fingerprint)"`.
*React:* the effect's dependency must be the derived value you render from, not the raw input it was derived from.

**B4 — §4.1 and §4.3 disagree on where the chip list is built, and the extra task buys nothing (§4.1 "Chip keys", §4.3 `ProgressSession.exerciseKeys`, §4.4 `@State keys`).** §4.1 computes chips "once per fingerprint change, not per render (120 Codable arrays)" in a `.task`, while §4.3's `ProgressSession` (built in `body` from the query rows) already carries every session's keys, so the Codable decode happens per render either way. Home and Program decode the same 120 `exercises` arrays per render today (`HomeView.swift:31`, `ProgramView.swift:36`, the M2 "scalar reads, safe while rendering" rule) with no measured cost, and a `.task(id:)` does not run "once per fingerprint" anyway (NB6). Two code paths building the same list is the kind of machinery the app does not need.
*Change:* delete `@State keys` and the chip task. `keys = ProgressStats.exerciseKeys(sessions:)` in `body` over the values mapped from the query rows; the one remaining task is the per-key fetch of B3. §4.4 "the two tasks of 4.1" → one task. AC-24 keeps "no `finishedLogs(` under `Features/Progress/`".
*React:* a `useMemo` around a selector that is already cheap to run in render.

**B5 — Unverified: the single session `@Query` admitting "current ∪ archived-completed" rows (§4.1 "Sessions", §5.6 "the builder's session predicate admits exactly these rows", AC-22).** This is the first cross-program read. The predicate needs a disjunction over an optional to-one hop, e.g. `$0.program?.id == programID || ($0.program?.archivedAt != nil && $0.statusRaw == completedRaw)`. Nothing in gotchas covers `||` with a `?.` hop or `archivedAt != nil` on a one-hop chain (only `== nil` is recorded, and it "also matches orphans"; the nested-`flatMap` rule was measured for two hops). If the shape misbehaves, the fallback is not a Swift-side filter over every session (that traverses `program` per row in `body`, NB1). Also, the query rows then span programs, and `body` maps `row.program?.id / createdAt / archivedAt` for every row: on 17.5 an upward to-one hop costs ~300 µs uncached (gotchas 2026-09-11), so 120 current + 120 archived rows ≈ 70 ms per `body`, and every save while the shell is mounted (shift, skip) re-runs the body of every query owner.
*Change:* (a) mark the predicate **unverified** in §4.1 and make AC-22's persistence test the settling probe on 17.5 and 26.5 (fixture: current program with pending + completed, archived program with pending + completed + one orphan session with `program == nil`; expect exactly current-all ∪ archived-completed, orphans excluded); the plan runs it as its first step. (b) Prefer the shape that needs no per-row traversal for the current program: **two queries** — `current` with the existing `HomeSnapshotBuilder.sessionPredicate(programID:)` (rows map to `isArchived = false`, `programID = program.id`, `programCreatedAt = program.createdAt`, no hop) and `archivedCompleted` with `$0.program?.archivedAt != nil && $0.statusRaw == completedRaw` (only these rows read `row.program`, ≤ 120 in v1). If (a) shows `program?.archivedAt != nil` is unreliable, the archived query can be `$0.statusRaw == completedRaw && $0.program?.id != programID`, filtered in Swift by `program?.archivedAt != nil`. (c) Record the measured `body` cost of the builder on `progress-history` rows on 17.5 in the plan (the m2-home researcher's method); if it exceeds a frame, move the archived mapping into the B3 task keyed on the fingerprint. The fingerprint (`HomeSnapshotBuilder.fingerprint`) is then over the concatenation of both row arrays.
*React:* two `useQuery` hooks with simple filters beat one query whose rows each need a join in render.

## Non-blocking

**NB1 — Reuse instead of parallel rules.** (i) §5.2 says top = `HomeStats.topWeightLb`, but the builder will compute `row.sets.filter(done).max()` inline like `finishedTops` (`WorkoutSnapshotBuilder.swift:81`); make the sentence literal by mapping the row's sets to `LoggedExerciseValue` and calling `HomeStats.topWeightLb`, so a future change to "done sets only" has one home. (ii) The `LoggedExercise` predicate (`exerciseKey == key && workout.flatMap { $0.finishedAt != nil } == true`) should be one shared static (`WorkoutSnapshotBuilder.finishedExercisePredicate(key:)`), used by `finishedTops` and the new `ProgressSnapshotBuilder.tops(key:in:)`, so the verified predicate is written once; the new function keeps every program and reads `log.session` (index, `scheduledDate`, program id, `createdAt`), dropping rows whose log has no session or program (total, never a trap). (iii) `month` is `weekStrip` over N days from the month start with a "completed wins, else lowest index" day rule that `weekStrip` (`HomeStats.swift:110-121`) and `ProgramTabStats.dayCells` (`ProgramTabStats.swift:113-122`) express as "lowest index" only. A completed + pending pair on one day is unreachable inside one program in v1, so "completed wins" is a harmless superset: extract one `HomeStats.session(on:date:in:calendar:)` used by all three, and `month` becomes a loop over that plus `sessionState`. Optional; if skipped, say in §5.5 that the rule is deliberately wider than the strip's.

**NB2 — Derive the DEBUG preselection in `body`, no `onAppear` write and no scroll token (§4.4 "Chip row", "DEBUG").** `effectiveKey(selected: selectedKey ?? preselection, keys:)` in `body` needs no handler, so the chip row's own `.onAppear` scroll sees the right key on the first pass (a parent `onAppear` that sets `selectedKey` after the child's `onAppear` would leave the deferred `scrollTo` targeting the old value: the `Task` captures the struct's value at call time, `WeekChipRow.swift:33-37`). Because the selection persists across tab returns (D1) and the `ScrollView` keeps its offset while mounted, no `scrollToken` is needed; `onAppear` alone covers the first show. Keep the "unknown key falls back" behaviour through `effectiveKey`. The AC-24 scan wording "inside the seed branch" should read "inside the root's `#if DEBUG` block, between `DebugSeed.parse(` and its `#endif`, like `preselection`" (`HomeGymLogApp.swift:47`, `MissedPromptSourceTests.swift:24-34`): `-progressExercise` works without `-seed`, exactly like `-programWeek`.
*React:* `const key = selected ?? defaultFromProps` in render instead of an effect that copies a prop into state.

**NB3 — Drop `ProgressPoint` and let `points(tops:)` return the sorted `[ProgressTop]`** (§4.3). The two types differ only by the ordering fields, which the chart summary and the tests also want (AC-16 asserts dates and weights). One type, one fewer mapping; B2's id goes on it.

**NB4 — `ProgramStore.archive(_:at:in:)` as the single writer of `archivedAt`, introduced by the seed** (§4.4 `progress-history`, "written only through store functions"). No writer of `archivedAt` exists today (`grep archivedAt` finds only the two predicates), so the seed would set the field by hand, which the spec's own rule forbids and INSIGHTS "Status invariants have one writer" argues against. `WorkoutLogStore.finish` was introduced in M2 for the seeder and reused by M3; do the same: a field writer through `StoreCommit.commit` (snapshot `archivedAt`), one save, guarded to a no-op when already archived; m4-settings' restart calls it and adds the "reset the tab to Home" step. Seed order: archived program via `ProgramStore.start` (Mon 08-03 06:00), complete its 12 sessions through `WorkoutLogStore.start`/`finish` as `MidProgramSeed` does, `archive` at 08-31 05:00, then `MidProgramSeed.populate` (its `start` guard passes because no current program remains). Add a persistence test that `ProgramStore.current` is nil after `archive` and the routing predicate no longer matches.

**NB5 — `ProgressView` needs `selectedTab` as a value, not a `Binding`.** It writes nothing (D1, §4.2); the Home link lives in `HomeView`. `let selectedTab: AppTab` is enough for the `.onChange(of: selectedTab)` `now` refresh (the Program-tab rule; keep both triggers per INSIGHTS 2026-09-11). `ShellView.screen(for:)` gains `case .progress: ProgressView(program: program, selectedTab: selected).id(program.id)`.

**NB6 — `.task(id:)` re-runs on every return to the tab, not once per fingerprint** (§4.1 wording). `.task` cancels when the view disappears and restarts on appear; `onAppear` fires on every return to a tab (verified on device for Program, INSIGHTS 2026-09-11). So the per-key fetch runs once per return to Progress (~55 ms worst case at program end on 17.5, a few ms mid-program) and once per fingerprint change while the tab is showing. Acceptable; say so in §4.1 and keep `points` across runs (B3) so a return never shows the empty line. Unverified for `.task` specifically (only `onAppear` was probed); the probe is a counter behind `-probeLog` on a scratch copy, not needed unless the cost shows up. Home's `finishedLogs` task has the same shape and is out of scope here.

**NB7 — Sort the session query by `(scheduledDate, index)` once rows span programs.** `index` alone leaves the relative order of an archived and a current row with the same index unspecified between fetches, so `HomeSnapshotBuilder.fingerprint` can change with no data change and re-run the B3 task spuriously. Harmless, but `(scheduledDate, index)` is stable and is already `HomeStats.ordered`'s order. Ties (same day, same index, restart-on-the-day-you-trained) stay harmless.

**NB8 — Chip `@State` lifetime is sound as specified (D1, AC-10).** `TabView(selection:)` keeps every tab's `NavigationStack` alive (INSIGHTS 2026-09-09), which is why the Program tab needs an explicit reset on every return (the user chose that over the default persistence, INSIGHTS 2026-09-11). `.id(program.id)` on the screen and the root's route flip (shell replaced by `WorkoutView`, then remounted after `finish`) give the resets D1 asks for without any code. AC-10 is the check; no probe needed.

**NB9 — Chart accessibility container is correctly marked unverified.** The researcher probed `.accessibilityElement(children: .ignore)` + label (wrapper element appears, XCUITest still lists the marks); `.contain` + label was not probed at all. AC-13's XCUITest half should assert only the hidden line/rules and the three dot label/value pairs, never the container's presence or order; VoiceOver's stop on the container stays the device check the spec names.

**NB10 — The per-render `body` cost applies while the tab is hidden too.** Every query owner re-runs `body` on every save (DTS, gotchas 2026-09-13), and the Progress screen stays mounted behind the other tabs, so a Home shift or skip re-runs the Progress mapping. With B5(b) the current rows are scalar reads and only archived rows hop to `program`; that keeps the extra cost of a shift under a frame in v1.

## Decisions to record in `insights/INSIGHTS.md` (once the spec is revised)

1. **Progress reads sessions through two queries**: the current program's (existing predicate, no `program` hop) and archived programs' completed sessions (`program?.archivedAt != nil && statusRaw == completed`, the only rows that traverse `program` in `body`); orphans excluded; the AC-22 result on 17.5 and 26.5 recorded next to it. First cross-program read in the app.
2. **Point identity across programs is the point's position**, never `PlannedSession.index` (indexes restart per program); ordering `(scheduledDate, programCreatedAt, index)`.
3. **An async per-key read is keyed on the effective (rendered) key and held as `(key, result)`**, drawn only when the held key equals the rendered key, never cleared before a re-fetch (generalizes the m3 pill baseline; `.task` re-runs on every tab return).
4. **`ProgressSession` wraps `SessionSummary`** with `programID`, `programCreatedAt`, `isArchived`; chips and the planned fallback derive from the wrapped `exercises` in `body` (no chip task).
5. **`ProgramStore.archive` is the single writer of `Program.archivedAt`** (introduced for the `progress-history` seed, reused by m4-settings' restart, the `finish` precedent).
6. **DEBUG preselections that are pure defaults are applied in `body`** (`selected ?? preselection`), not copied into `@State` in `onAppear`; extends the 2026-09-11 `@Entry` pattern.
