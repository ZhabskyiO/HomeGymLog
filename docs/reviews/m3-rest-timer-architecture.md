**Verdict: approve with changes.** The data model, writer shape, Engine split and the swipeable-during-rest decision all conform to the recorded decisions and to the researcher's verified facts. Four items need a concrete answer before planning: two are spec gaps a planner would have to guess at (the scroll inset's height, the announcement's trigger site), one is an unrunnable acceptance criterion (countdown behaviour tested from a frozen-clock seed), and one is a race in the notifier reconciliation.

## Blocking

**B1. §2.2 / §2.4 / §6 "Content taller…": the "extra bottom space equal to the overlay's height" has no source for the height.**
The spec quotes "about 148 pt on iPhone 15" (a measurement from `/Users/zhabskyi/AppleApps/HomeGymLog/docs/reviews/m3-rest-timer-researcher.md` Q4), but the overlay's height is 20 + 84 + 10 + the device's bottom safe area, which varies (34 pt on iPhone 15, 0 on a home-button iPhone) and grows with Dynamic Type. With `.overlay(alignment: .bottom)` the content has to be padded by a number the view must either hardcode (wrong on other devices) or measure (a `GeometryReader`/`onGeometryChange` round-trip into `@State`, new plumbing).
Fix: swap the existing `.safeAreaInset(edge: .bottom)` content instead of stacking an overlay on top of it: `if rest != nil { RestOverlay(...) } else { WorkoutBottomBar(...) }` in `/Users/zhabskyi/AppleApps/HomeGymLog/HomeGymLog/Features/Workout/WorkoutLoggingContent.swift` lines 65–73. The inset then sizes itself to whatever it contains, the scroll content is automatically kept clear of it and still scrolls under it (the tab-pill precedent in INSIGHTS "Tab bar is TabView + hidden system bar + safeAreaInset pill", verified on 17.5 and 26.5), the bar is unreachable by touch and VoiceOver because it is not in the tree (no `accessibilityHidden` needed), and "Next exercise ›" stays covered exactly as decision 8 requires. **Unverified**: the researcher probed only the `.overlay` placement (fact 16 lists the inset alternative as unprobed). Probe: `-seed wo-rest` screenshot on 17.5 and 26.5, overlay top at y ≈ 704 / 726 as in the researcher's table, plus a scroll of a 4-set fixture until row 4 clears the card. If the probe fails, the fallback is the `.overlay` plus a measured height, and the spec must then say the measurement mechanism.
React analogy: a sticky footer whose height the layout already accounts for (`safeAreaInset`) instead of `position: absolute` plus a hand-computed `padding-bottom`.

**B2. §5.5 / §4.1: "the screen runs it on every tick" has no trigger site, and the only naive one is a `@State` write inside `body`.**
`observeEnd` returns a new `lastSeenEndsAt'` that the screen "stores". A tick is a re-evaluation of the `TimelineView` closure, i.e. of `body`; writing `@State` there is a runtime "Modifying state during view update" warning with undefined ordering. The spec has to name the effect the rule runs in.
Fix: compute `resting` (a `Bool`) inside the timeline closure and attach `.onChange(of: resting)` plus `.onChange(of: log.restEndsAt)` to the content; the handler calls `RestTimer.observeEnd(lastSeenEndsAt: lastSeen, restEndsAt: log.restEndsAt, resting: resting, now: clock.now())`, posts when `announce`, and writes `lastSeen`. `.onChange(of: scenePhase)` (already needed for `removeDelivered`) sets `lastSeen = nil` on leaving `.active`. The pure rule and its table stay exactly as written. **Unverified**: that `.onChange(of:)` on a value derived inside a `TimelineView` closure fires on iOS 17.5 at the tick that flips it. Probe: the researcher's 6 s live-rest probe with a `-probeLog` line from the `onChange` handler, expecting one line 11–17 ms after `restEndsAt`.
React analogy: side effects go in `useEffect(..., [resting])`, never in the render function.

**B3. §8 AC-5, AC-7: countdown behaviour is specified from frozen-clock seeds, where it cannot happen.**
`-seed wo-rpe` runs `AppClock.frozen` (`/Users/zhabskyi/AppleApps/HomeGymLog/HomeGymLog/App/DebugSeed/DebugSeed.swift` line 50–52); the spec's own §4.4 says "on a frozen seed clock the label never moves". So "tap 7: overlay 1:15 → 1:14 … then gone" (AC-5) and "the overlay outlives the original end" (AC-7) can never be observed there, and the seed's `SilentRestNotifier` makes AC-6's "no banner" pass vacuously. AC-9 already says "(on-disk store)", so the intent is clear.
Fix: state at the top of the Behavior block that AC-5–AC-11 run from a production launch (Home → Start workout on the on-disk store), and rewrite AC-5/AC-7's entry points accordingly ("rate set 1 of a freshly started workout" rather than "from `-seed wo-rpe`"). Seeds remain screenshot-only (AC-1–AC-4).

**B4. §2.5 / §3 "Notification reconciliation": two `schedule` calls can land out of order and leave the pending request at the wrong instant.**
`.task(id: log.restEndsAt)` cancels the previous task when the id changes (Apple-documented; not probed here), but `LiveRestNotifier.schedule` continues after its `await requestAuthorization` regardless of cancellation and calls `center.add` with the `endsAt` it captured. Two quick "+30s" taps (or a +30s during the fast already-determined authorization round-trip) produce two adds under one identifier; the researcher verified only sequential replacement (600 s then 300 s), not concurrent order. If the older add lands last, the banner fires 30 s before the overlay ends.
Fix: in `schedule`, `guard !Task.isCancelled else { return }` after every `await` (the task's cancellation flag is set even though the awaited completion-handler call is not interruptible); the same guard covers a `schedule` still awaiting when the screen disappears and `onDisappear` has already cancelled. State this in §4.3's notifier row and add a recording-double test: a second `schedule` that starts before the first resumes leaves exactly the newer instant recorded. **Unverified** platform claim: `.task(id:)` cancellation on id change; probe: a `-probeLog` line from the post-await guard during a double +30s.
React analogy: the "ignore stale responses" flag in an effect whose dependency changed while a fetch was in flight.

## Non-blocking

1. **§4.3 `RestNotifier` seam shape.** The house precedent for an injected service is a struct of closures (`AppClock` in `/Users/zhabskyi/AppleApps/HomeGymLog/HomeGymLog/App/AppClock.swift`: `.live()`, `.frozen()`), not a protocol plus an `any` existential. A `struct RestNotifier { var schedule: (Date, AppClock) async -> Void; var cancel: () -> Void; var removeDelivered: () -> Void }` with `.live()`, `.silent()` and a test-side `.recording(into:)` gives the same three "conformers" with no protocol, and matches `@Entry var appClock`. Either compiles; the protocol is acceptable if the planner prefers the researcher's sketch, but record which.
2. **§4.3 default value and the nil-by-default rule.** `@Entry var restNotifier = SilentRestNotifier()` is not the nil-by-default pattern: it is a service whose default is the *non-production* behaviour, so forgetting to set the live one at the root fails silently in Release. Two acceptable shapes: (a) default `.live()` like `appClock`, with the DEBUG seed branch overriding to `.silent()` (production never sets it, exactly the pattern); or (b) keep the silent default and make the root set it unconditionally as a plain local decided before `#if DEBUG` (the `clock` shape in `/Users/zhabskyi/AppleApps/HomeGymLog/HomeGymLog/App/HomeGymLogApp.swift` lines 20–41), plus a static test that `HomeGymLogApp.swift` mentions `LiveRestNotifier` (or `.live()`). (a) is simpler; (b) keeps previews quiet. Record the choice in INSIGHTS.
3. **§4.3 file placement.** `RestNotifier` imports `UserNotifications` and M4's daily reminder will need the same authorization request and center; if it lives in `Features/Workout/`, M4 either imports a feature's internals or duplicates it. Put it beside the clock in `App/` (the `@Entry` already goes into `App/AppClock.swift`), leaving `Features/Workout/` with only `RestOverlay.swift`.
4. **§4.3 `RestNotificationPlan.decide` duplicates the notifier's pre-await guard.** The live notifier also does `guard endsAt > clock.now() else { cancel() }` before the await. One rule, one place: keep `decide` (it is what AC-23 tests) and let `schedule` keep only the post-await `interval > 0` guard, which exists for a different reason (the 0 s trigger terminates the app).
5. **§8 AC-11 "VoiceOver announces the overlay once when it appears" has no mechanism.** Nothing in §2.6 or §4.3 posts anything at rest start; a combined accessibility element does not announce itself on appearance. Either drop the clause or specify an `AccessibilityNotification.LayoutChanged` post (focus argument optional) when `resting` flips to true, in the same `.onChange` as B2. **Unverified** either way (the simulator has no VoiceOver); the user's device pass is the probe. Likewise "value reads as minutes and seconds" needs a Shared function (`RestText.spoken(seconds:)`, e.g. 62 → "1 minute 2 seconds") that §4.3 and AC-22 do not list.
6. **§2.6 announcement API, unverified.** `AccessibilityNotification.Announcement("Rest over").post()` is iOS 17.0 (no `#available` needed), but whether an announcement posted in the same effect that removes the overlay is spoken, or is pre-empted by VoiceOver's own layout speech, is unprobed. Probe: device, VoiceOver on, one rest to zero. If pre-empted, the fallback is `UIAccessibility.post(notification: .announcement, ...)` from a `Task` that yields once (`await Task.yield()`); note it in the plan as the alternative, not as spec.
7. **§4.4 whole-content 1 Hz re-evaluation.** Accepting it is fine (`WorkoutLoggingContent` takes closures, so SwiftUI re-evaluates it whenever its parent does anyway; the researcher's R4/R8 ran the real screen). Two notes for the plan: the outer timeline's `from:` anchor only changes when the active row's identity changes too (rest starts from RPE pending, where no `SetSwipeRow` exists; clears coincide with the row becoming done), so `dragX` cannot be lost by the anchor switch; and if AC-17 hitches, the named fallback is an outer timeline that computes only `resting: Bool` and hands it to a content view whose handlers are stable (`WorkoutView` methods, not per-render closures). The overlay's own inner timeline is then still the one drawing the label and ring.
8. **§4.2 "start rest if a pending set remains" inside the store is the right place.** It is the single writer of the "rest exists ⇒ a pending set exists" relation, so the seed, the tests and the screen cannot disagree. The `set.exercise?.workout` upward hops and the 15-set traversal cost about 1–2 ms on 17.5 on a write path, not in `body`, so the retention/traversal gotchas do not apply. Keep it; do not pass the decision from the caller.
9. **§4.2 call-site count.** The tests hold 25 `setRPE`/`skipRPE` call sites (16 + 6 + 2 + 1), not 30 (19 + 7 + 3 + 1), plus three in `/Users/zhabskyi/AppleApps/HomeGymLog/HomeGymLog/App/DebugSeed/WorkoutSeed.swift` and two in `WorkoutView.swift`. Planner budget only.
10. **§4.2 `finish` and stale rest fields.** Every path into Summary clears the rest (the three rest-starting writers clear when nothing is pending; `nextExercise` and `logSet` clear), so a finished log carries nil by construction; no routing predicate, Home mapping or summary rule reads the two fields, so a stale pair on an in-progress log breaks nothing. Leave `finish` untouched as specified, but record the invariant (below) so M4 history views do not start reading `restEndsAt` as "had a rest".
11. **§4.3 `RestTimer.display` and the wording question.** With "Rest over" alone nothing changes. With "Rest over. Next: set 2 of 3", the label is needed at a moment when `resting` is already false, so `display` returns nil; split `RestTimer.next(exercises:state:) -> RestNext?` out of `display` and have both the overlay and the announcement call it, rather than caching the last resting frame in `@State`. Recommend "Rest over" alone (one string, no split).
12. **§8 / views.** `WorkoutView.body` is 49 lines today (`/Users/zhabskyi/AppleApps/HomeGymLog/HomeGymLog/Features/Workout/WorkoutView.swift` lines 47–95); the timeline wrapper, `.task(id:)`, two `.onChange`s and `.onDisappear` add roughly 20–25. If it passes 80, extract the notification and announcement effects into one `ViewModifier` in `Features/Workout/` (a one-caller modifier is the standard way to split modifiers; not new machinery).
13. **§2.5 `onDisappear` cancel (fact 16, unverified).** The spec marks it and AC-16 covers it on device; add the simulator probe to the plan since it is cheap: `-probeLog` pending count after Exit → Discard mid-rest on 17.5 and 26.5. If `onDisappear` proves unreliable when the root swaps the branch, the fallback is cancelling in `discard()` before the delete (the screen still owns the notifier), not in the store.

## Decisions to record in `insights/INSIGHTS.md`

- **Rest fields are nil on every finished log by construction; only the workout screen reads them, always gated on `now < restEndsAt`.** M4 history and Progress must not read `restEndsAt` as "a rest happened".
- **Notifier seam**: the shape (struct of closures per `AppClock`, or the protocol), where it lives (`App/`), and the default rule chosen from NB2 (live default overridden by the seed branch, or silent default set unconditionally at the root). Seeds, previews and tests never touch the system center; the identifier `rest-timer` belongs to this slice.
- **M4 delegate rule**: if M4 installs a `UNUserNotificationCenterDelegate` for the reminder's foreground banner, it must return `[]` for the `rest-timer` identifier (this slice's verified "foreground shows nothing" fact must survive), use a different identifier for the reminder, be installed in `App.init` and be retained (the delegate property is weak).
- **Effects from a `TimelineView` tick run in `.onChange` on a derived value, never as a `@State` write in `body`** (B2).
- **Async notifier work checks `Task.isCancelled` after every await** (B4), because `.task(id:)` cancels the task, not the system call it is awaiting.
- **Behaviour ACs that depend on time passing run on a live clock**; `-seed` launches freeze the clock and inject the silent notifier, so they are screenshot-only.
- **Overlay placement**: the `safeAreaInset` swap (B1) if the probe passes, with its measured y-origins on 17.5 and 26.5.
